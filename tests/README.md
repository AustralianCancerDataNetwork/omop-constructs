# Running the test suite

## Quick start

```bash
# Unit tests only
uv run --extra dev python -m pytest -m "not postgres"

# PostgreSQL integration test
export ENGINE_CDM='postgresql+psycopg://user:pass@localhost:5432/dbname'
uv run --extra dev python -m pytest -m postgres -v

# Registry schema snapshot artifact
uv run --directory . omop-constructs schema-snapshot tests/artifacts/construct_registry_schema.csv

# Equivalent module invocation
python -m omop_constructs.core.schema_snapshot tests/artifacts/construct_registry_schema.csv

# Regenerate the checked-in full-registry artifact using the Postgres fixture
UPDATE_REGISTRY_SCHEMA_SNAPSHOT=1 \
uv run --extra dev python -m pytest tests/test_registry_schema_artifact_postgres.py -m postgres -q
```

## Construct contract tests

`construct-contracts.toml` at the repository root is the D3 grain catalogue. Two
test modules keep it honest:

- `test_construct_contracts.py` — registry coverage and key-column validation.
  Fails when a registered construct has no declared grain, when a contract names
  a construct that is no longer registered, or when a declared key names a
  column absent from either the mapper or the materialized-view select.
- `test_construct_catalogue_render.py` — fails when `docs/construct-catalog.md`
  is out of step with the manifest. Needs no database.

Declared keys in the manifest are *intended* keys, and most are violated today
by design. These tests never assert that a key holds against data; measuring
that needs a populated CDM and belongs to the release validation scripts.

```bash
# Regenerate the catalogue after editing the manifest
python -m omop_constructs.core.catalogue docs/construct-catalog.md
# or
uv run --directory . omop-constructs render-catalogue docs/construct-catalog.md

# Summarise the manifest without a database
uv run --directory . omop-constructs contracts --verbose-contracts
```

## Mapper warnings

`test_mapper_warnings_are_errors.py` imports the full construct manifest in a
subprocess with `SAWarning` promoted to an error. A clean single import is
warning-free, so a new mapper identity conflict fails here rather than hiding
among the reload warnings the rest of the suite produces (OC-M4).

The subprocess is deliberate: in-process the result would depend on whatever
earlier tests had already imported, which is the state that generates those
warnings.

## Release validation scripts

`test_release_validation_sql.py` covers the SQL generated by
`scripts/release_validation/` against synthetic views with hand-computed
expected numbers — duplicate counts, NULL-key counts, multiplicity changes, and
per-person deltas. Run it before trusting a comparison produced in a secure
environment, where the output cannot be checked against a known truth.

## PostgreSQL integration test

The `postgres`-marked test is opt-in and requires a reachable PostgreSQL
database. The fixture resolves the integration source in this order:

1. the configured `cdm_db` resource from `oa-configurator`
2. `ENGINE_CDM`
3. `ENGINE`

When a stack config is present, the fixture reuses the effective `cdm_db`
schema specification and writes a temporary stack config that points `cdm_db`
at the disposable scratch database. Resolver-backed construct imports therefore
exercise the same `oa-configurator` path as normal runtime code while remaining
isolated from the configured database.

The test does not modify the configured source database directly. Instead it:

1. connects to that server
2. creates a disposable scratch database with a generated unique name
3. bootstraps the OMOP tables into the configured CDM and vocabulary schemas
4. runs the full registry compile check
5. creates all materialized views with `WITH NO DATA`
6. drops the scratch database on teardown

If a generated scratch database name already exists, the fixture fails instead
of dropping a pre-existing database during setup.
